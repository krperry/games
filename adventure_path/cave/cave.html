The Cave of the Golden Box

This is the game that the Unit, Item, Player, and Room classes were built for. You start in a dark tunnel at the edge of a cave. Somewhere in the cave’s nine dark rooms lies a little gold box. Find it, pick it up, and get back to the tunnel before you run out of strength, or a grue will find you first.

Games like this are called text adventures, or interactive fiction. They are among the oldest computer games, and they have always been popular with blind players, because the whole world is made of words.

In this lesson you will see how the classes fit together to build a world, and how the game understands commands the player types.

A Note on Reading Code with a Screen Reader

Python uses indentation, the spaces at the start of a line, to show which lines belong together. A line that ends with a colon, such as while True: or def main():, starts a block. Every line in that block is indented four more spaces than the line with the colon.

Before you start, turn on indentation reporting in your screen reader or code editor so you hear how far each line is indented. In NVDA this setting is called “Line indentation reporting” and is under Document Formatting. JAWS and most code editors have a similar setting. Many blind programmers like to hear indentation as tones, but spoken numbers work too.

It also helps to set your screen reader to read all punctuation while you are working with code. Punctuation matters in Python. A missing colon, quote, or parenthesis is one of the most common errors.

In this lesson, code you type into a file is shown in code blocks. Code you type into the interactive shell starts with three greater-than signs, >>>. That is the shell’s prompt. Do not type the prompt. Type only what comes after it. The lines with no prompt are what Python prints back.

How to Play

You start in the Dark Tunnel with 8 health points. Each time you move to another room, you lose one. Type a direction to move: north, east, south, or west. You can type just the first letter or two, such as n or we.

When you find the gold box, type get and its name, such as get box. Then return to the Dark Tunnel. If you get there with the box, you win. If your health runs out before then, you lose.

The cave is a three-by-three grid of rooms, with the tunnel below the middle of the bottom row:

  • Top row: rooms 1, 2, and 3
  • Middle row: rooms 4, 5, and 6
  • Bottom row: rooms 7, 8, and 9
  • The tunnel, room 0, is south of room 8

The box is placed at random in one of the rooms, but never in the center room, 5, or the entrance, room 8.

How the Program Is Organized

cave.py has four parts, from top to bottom:

  1. Import the modules and classes.
  2. Build the world: the rooms, how they connect, the player, and the box.
  3. Define the functions that handle commands and check for a win.
  4. Run the command loop in main().

The first two parts are not inside any function. They run as soon as the file is loaded, so the world is ready before main() starts.

Importing the Classes

import time
import random

import sys


from room import Room

from player import Player

from item import Item

random.seed(time.time())

Each class is imported from its own file. Python finds room.py, player.py, and item.py because they are in the same folder as cave.py. You do not need to import Unit here. The other classes import it themselves.

random.seed() sets the starting point for the random number generator. Seeding with the current time was common in older programs, but Python already does this for you automatically, so this line is not needed. Seeding is useful when you want the same random results every time, for testing. Try random.seed(1) and the box will be in the same room every game.

This is a dark dank tunnel of a cave.

rooms is a list of ten Room objects, made right inside the list. rooms[0] is the tunnel, and rooms[1] through rooms[9] are the cave. Each room gets an id, a title, and a description.

Multi-line Strings

Each description is in triple quotes. A triple-quoted string can go over several lines, and the line breaks are part of the string. Each description starts with two line breaks, then the text, then one more line break. That is where most of the blank lines in the game’s output come from.

Blank lines can be a help or a hindrance by ear. One blank line between parts is a nice pause. Several in a row just mean more arrow key presses when you review the output. You can remove the extra line breaks from the descriptions in an exercise.

Connecting the Rooms

# cave1 exits
rooms[1].set_direction("east", rooms[2])
rooms[1].set_direction("south", rooms[4])

These lines build the map. rooms[1].set_direction("east", rooms[2]) means “going east from room 1 leads to room 2.” Every connection has to be made in both directions. Room 2 also has rooms[2].set_direction("west", rooms[1]). If you forget one direction, the player can go somewhere but never come back.

Because the map is built from these lines, you can make a new cave just by changing them. Making a map from a list of connections like this is a simple kind of graph, a structure computer scientists use for maps, networks, and much more.

Some room titles do not match their place on the map. Room 1 is in the top left, but its title is “Dark Northeast Corner,” and room 3, in the top right, is “Dark Northwest Corner.” For a player who builds a map in their head, wrong directions in titles are confusing. Fixing them is an exercise.

Placing the Box at Random

i = random.randint(0, 6)

rooms[randRooms[i]].add_item(item)

randRooms is the list of rooms the box can be in. The program picks a random index from 0 to 6 and puts the box in that room.

Read rooms[randRooms[i]] from the inside out: i is a random index, randRooms[i] is a room number, and rooms[...] is that room. You could do the same thing more simply with random.choice(randRooms).

Commands

The game understands five commands: get, north, east, south, and west. They are stored in a dictionary near the bottom of the file:

commands = {
    "get": do_get,
    "north": do_move,
    "east": do_move,
    "south": do_move,
    "west": do_move,
}

A Dictionary of Functions

The values in this dictionary are functions! Notice there are no parentheses after do_get and do_move. The dictionary holds the functions themselves, not the result of calling them. In Python, a function is a value like any other. You can put it in a variable, a list, or a dictionary, and call it later.

>>> def hello():
...     print("Hi!")
...
>>> greet = hello
>>> greet()
Hi!

So commands["get"] is the do_get function, and commands["get"]("get", "box") calls it. This is called a dispatch table. It is a clean way to match commands to the code that runs them, without a long chain of if and elif. To add a new command, you write a function and add one line to the dictionary.

All four directions use the same function, do_move(). It knows which way to go because the command name is passed to it.

Understanding a Command

When the player types something, command_args() turns it into a function to call and the arguments to give it.

def command_args(input_string):
    args = input_string.split(" ", 1)

    if len(args) < 2:
        args.append("")

split()

split() breaks a string into a list of words. The first argument is what to split on, here a space. The second is the most splits to make. With 1, it splits only at the first space, so everything after the command stays together.

>>> "get little box".split(" ", 1)
['get', 'little box']
>>> "north".split(" ", 1)
['north']

If the player typed just one word, there is nothing after it, so the program adds an empty string. Now args always has two items: the command word and the rest.

Short Commands

        args[0] = get_long_command(args[0])
def get_long_command(cmd):
    """get the long version of a short command"""

    for command in commands:
        if cmd == command[: len(cmd)]:
            return command
    return cmd

This lets the player type n for north, or ge for get. Looping over a dictionary gives you its keys, so command is each command name in turn.

command[: len(cmd)] is a slice of the start of the command name, as long as what the player typed. If the player typed n, the slice of "north" is "n", which matches. The first command that matches is returned.

Short commands are a big help for players who use screen readers, who often type quickly and do not want to type north over and over.

try and except

    try:
        args[0] = get_long_command(args[0])

        # return a 3 part tupple             function, cmd, and args

        return (commands[args[0]], args[0], args[1])

    except:
        return None

If the player types a word that is not a command, commands[args[0]] causes a KeyError. Normally that would stop the program. A try block lets you catch errors. If any line in the try block causes an error, Python jumps to the except block instead of stopping.

>>> try:
...     number = int("hello")
... except ValueError:
...     print("That is not a number.")
...
That is not a number.

Here, the except returns None, which means “not a command.”

This except does not name an error, so it catches every kind of error. That is called a bare except, and it is risky, because it can hide real bugs. If you made a typo inside the try block, the game would just say “No such command” and you would never hear the real error. Writing except KeyError: catches only the error you expect.

If it works, the function returns a tuple of three things: the function to call, the command name, and the rest of what the player typed.

The Command Functions

Moving

def do_move(cmd, args):
    if player.can_move(cmd):
        player.move(cmd)

        player.lose_health()

        check_win()

    else:
        print("You can't go that way")

For a move, the command name is the direction. If there is an exit, the player moves, loses one health, and the game checks whether they won or lost.

Getting an Item

def do_get(cmd, args):
    take_item = player.get_location().remove_item(args)

    if not take_item:
        print(f"No {args} found.")

    else:
        player.add_item(take_item)

        print(f"You pick up {take_item.get_title()}.")

The rest of the command, such as box, is passed to the room’s remove_item(), which finds and removes an item with that name. If it worked, the item goes into the player’s inventory.

Both functions take the same two parameters, cmd and args, even though do_move() does not use args and do_get() does not use cmd. Functions in a dispatch table all need to be called the same way.

Winning and Losing

def check_win():
    if player.health < 1 and not player.items:
        ...
        sys.exit()

    if player.health < 1 and player.get_location() == rooms[0] and player.items:
        ...
        sys.exit()

    if player.get_location() == rooms[0] and player.items:
        ...
        sys.exit()

After every move, the game checks three cases:

  1. Out of health without the box: the grue gets you.
  2. Out of health, but you just made it to the tunnel with the box: a close win.
  3. Back in the tunnel with the box, with health to spare: a clean win.

player.get_location() == rooms[0] checks whether the player’s room is the tunnel. For objects like rooms, == checks whether they are the same object.

Think about a fourth case: out of health, carrying the box, but not in the tunnel. None of the checks match, so the game goes on. But the player has no health left. Every move makes it go lower, and the game never ends until they reach the tunnel. That is probably not what was intended.

The Command Loop

def main():
    print("Welcome to the dark caves of the Golden box")
    ...
    print(player.get_location().get_room_string())

    command = "start"

    while command not in "quit":
        command = input("enter a command >")

        targs = command_args(command)

        if targs:
            targs[0](targs[1], targs[2])

        else:
            print("No such command.")

main() reads the instructions, describes the first room, and then runs the command loop. Each time through, it reads a command, turns it into a function and arguments, and calls the function. targs[0](targs[1], targs[2]) calls the function stored in the tuple, passing it the command name and the rest.

The Quit Bug

Listen closely to the loop condition: while command not in "quit". With a string after it, in checks whether one string is inside another. So the loop ends if the command is "quit", but also if it is "q", "u", "it", or even an empty string, because the empty string is inside every string.

>>> "quit" in "quit"
True
>>> "q" in "quit"
True
>>> "" in "quit"
True

So if the player presses Enter without typing anything, the game ends. And the check happens at the top of the loop, after the command was already handled. quit is not in the commands dictionary, so when the player types quit, the game first says No such command. and then ends.

What was probably meant is while command != "quit":, or better, a quit command in the dispatch table.

Finding the Mistakes by Playing

Many of this game’s problems are easy to find just by playing it and listening carefully. Here is what a careful player will hear:

  • The welcome says you have 9 health points, but the player starts with 8.
  • If you run out of health.ou will no longer is missing the Y, and has a period in the middle of the sentence.
  • eatten should be eaten, and Your dead and Your a winner should use You're.
  • collapse.A big hairy Grue is missing a space, because two strings are joined with +.
  • a little Gold boxis laying is missing a space, and should say “lying.” That one comes from Room.get_items_string().
  • get gold box does not work, because the name has a capital G.
  • quit says No such command. before quitting, and pressing Enter on an empty line quits.

Typos in messages matter more by ear than by eye. A sighted reader skims past a missing space. A screen reader reads boxis as one strange word.

Summary

You studied a complete text adventure built from classes. You learned that:

  • A world can be built from objects in a list, connected with method calls.
  • Triple-quoted strings can span several lines, and their line breaks are kept.
  • A dictionary can hold functions. Calling one from the dictionary is called dispatching.
  • split(" ", 1) splits a string at the first space.
  • A slice like command[:len(cmd)] lets players type short commands.
  • try and except catch errors. Name the error you expect, instead of using a bare except.
  • in with two strings checks whether one is inside the other, which can cause surprising bugs.
  • Playing your own game and listening carefully is a great way to find bugs.
