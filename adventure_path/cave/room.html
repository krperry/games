The Room Class

A cave adventure is a world of rooms. Each room has a title, a description, a list of exits that lead to other rooms, and sometimes an item lying on the ground. The Room class holds all of that, and it can describe itself to the player in words.

This class introduces the dictionary, a way to look up a value by a name instead of a number. It is also a good place to practice reading code carefully, and to think about the assumptions a piece of code makes. A file in the same folder, room.lnt, shows the report from a tool that checks code for problems.

Topics covered in this lesson

  • Dictionaries
  • Looping over a dictionary with items()
  • Building a description string for a screen reader
  • is None and is not None
  • Changing a list while you loop over it
  • Linters and what they report
  • Tracing code and spotting the assumptions it makes

A Note on Reading Code with a Screen Reader

Python uses indentation, the spaces at the start of a line, to show which lines belong together. A line that ends with a colon, such as while True: or def main():, starts a block. Every line in that block is indented four more spaces than the line with the colon.

Before you start, turn on indentation reporting in your screen reader or code editor so you hear how far each line is indented. In NVDA this setting is called “Line indentation reporting” and is under Document Formatting. JAWS and most code editors have a similar setting. Many blind programmers like to hear indentation as tones, but spoken numbers work too.

It also helps to set your screen reader to read all punctuation while you are working with code. Punctuation matters in Python. A missing colon, quote, or parenthesis is one of the most common errors.

In this lesson, code you type into a file is shown in code blocks. Code you type into the interactive shell starts with three greater-than signs, >>>. That is the shell’s prompt. Do not type the prompt. Type only what comes after it. The lines with no prompt are what Python prints back.

The Source Code for Room

Type this program and save it as room.py in the cave folder:

"""Class to contain the room information"""
from unit import Unit

1


class Room(Unit):
    """
    This class defines the room type dirived from Unit
    """

    def __init__(self, location, title, desc):
        """Constructor"""
        super().__init__([], title, desc)
        self.location = location
        self.exits = {"north": None, "east": None, "south": None, "west": None}
        self.items = None

    def set_direction(self, direction, location):
        """Set the location this a given exit leads to"""
        self.exits[direction] = location

    def add_item(self, item):
        """Add an item to this rooms contents"""
        if not self.items:
            self.items = []
        self.items.append(item)

    def get_item(self, name):
        """get an item from this room by given name"""
        i = self.items[name]
        del self.items[name]
        return i

    def get_room_string(self):
        """Get rooms full description"""
        return (
            f"{self.title}\n{self.description}\n"
            + f"You can walk {self.directions()}\n{self.get_items_string()}\n"
        )

    def directions(self):
        """return direction string"""
        dir_str = ""
        for direction, room in self.exits.items():
            if room != None:
                dir_str += direction + ", "
        return f"[{dir_str.strip().strip(',')}]"

    def has_exit(self, direction):
        """Returns if this room has a given exit"""
        return self.exits[direction]

    def get_items_string(self):
        """Gets description of items in the room"""
        if not self.items:
            return ""
        for item in self.items:
            item_str = item.get_title() + "is laying on the ground.\n"
        return item_str

    def remove_item(self, item):
        """Remove this item from room"""
        if not self.items:
            return None
        for i in range(len(self.items)):
            if self.items[i].is_name(item):
                tItem = self.items[i]
                del self.items[i]
                if len(self.items) < 1:
                    self.items = None
                    return tItem
        return None

A Stray Line

from unit import Unit

1

There is a line that holds only the number 1. It is a complete Python statement that makes the number 1 and then throws it away. It does nothing. It was probably typed by accident. You can delete it.

Lines like this are easy to miss by eye and easy to miss by ear. Tools called linters, which you will meet at the end of the lesson, are good at finding them.

The Room Constructor

class Room(Unit):
    def __init__(self, location, title, desc):
        """Constructor"""
        super().__init__([], title, desc)
        self.location = location
        self.exits = {"north": None, "east": None, "south": None, "west": None}
        self.items = None

Room inherits from Unit. Players never type a room’s name, so the room passes an empty list as its names.

location is a short id for the room, such as "cave0". It lets the programmer tell rooms apart, but the game never says it out loud.

Dictionaries

        self.exits = {"north": None, "east": None, "south": None, "west": None}

This is a dictionary. A dictionary holds pairs. Each pair has a key and a value, joined by a colon. Pairs are separated by commas, and the whole thing is inside curly braces.

A list looks up values by number: my_list[0]. A dictionary looks up values by key: self.exits["north"]. That is perfect for exits, because a direction name is much clearer than a number.

Here, every direction starts with the value None, meaning there is no exit that way. The game will replace some of them with rooms.

Try a dictionary in the shell:

>>> ages = {"Ana": 12, "Ben": 14}
>>> ages["Ana"]
12
>>> ages["Cam"] = 11
>>> ages
{'Ana': 12, 'Ben': 14, 'Cam': 11}
>>> ages["Dee"]
Traceback (most recent call last):
  ...
KeyError: 'Dee'

Putting a value in with a new key adds a pair. Looking up a key that is not there causes a KeyError.

With a screen reader, listen for the colons and commas to tell the keys and values apart. A dictionary written one pair per line is much easier to follow:

        self.exits = {
            "north": None,
            "east": None,
            "south": None,
            "west": None,
        }

Setting an Exit

    def set_direction(self, direction, location):
        """Set the location this a given exit leads to"""
        self.exits[direction] = location

This puts a room in the dictionary under a direction. In the game, rooms[0].set_direction("north", rooms[8]) means “going north from room 0 leads to room 8.”

The parameter is named location, but it holds a whole Room object, not a location id. A name like room would be clearer.

Describing the Room

    def get_room_string(self):
        """Get rooms full description"""
        return (
            f"{self.title}\n{self.description}\n"
            + f"You can walk {self.directions()}\n{self.get_items_string()}\n"
        )

This builds everything the player hears when they enter a room: the title, the description, the ways out, and any items. \n starts a new line, so each part is on its own line, and your screen reader can read them one at a time.

The whole expression is in parentheses so it can be split over two lines. The two f-strings are joined with +.

The method calls two other methods to build its parts. Each part is easier to fix when it is its own method.

Listing the Directions

    def directions(self):
        """return direction string"""
        dir_str = ""
        for direction, room in self.exits.items():
            if room != None:
                dir_str += direction + ", "
        return f"[{dir_str.strip().strip(',')}]"

Looping over a Dictionary with items()

self.exits.items() gives you each key and value as a pair. The for loop takes them apart into two variables, direction and room, the same way enumerate() gave you an index and an item.

>>> exits = {"north": "hall", "south": None}
>>> for direction, room in exits.items():
...     print(direction, room)
...
north hall
south None

Dictionaries keep their pairs in the order they were added, so the exits are always listed north, east, south, west.

is None

The if line checks room != None. That works, but Python programmers write room is not None instead. is checks whether two things are the very same object, and there is only one None, so is is the right test for it. The linter report for this file points this out.

Cleaning Up the String

The loop adds a comma and space after every direction, so it might build "north, east, ". Then strip() removes the space at the end, and strip(',') removes the comma. The result goes in square brackets: [north, east].

The square brackets look like a list. By ear, your screen reader might say “left bracket north comma east right bracket,” which is a lot of noise. A plain sentence is easier to hear, such as You can walk north or east.

Does the Room Have an Exit?

    def has_exit(self, direction):
        """Returns if this room has a given exit"""
        return self.exits[direction]

This returns the room in that direction, or None. The docstring says it returns whether there is an exit, and since a room counts as True and None counts as False, it can be used that way.

Items in a Room

    def add_item(self, item):
        """Add an item to this rooms contents"""
        if not self.items:
            self.items = []
        self.items.append(item)

This works like Player.add_item(). The list is made the first time an item is added.

Reading the Rest of the Methods

The cave game is designed with exactly one item, the little gold box, and it is placed in exactly one room. So a room holds either no items or one item. The rest of the Room methods are written with that design in mind. Read each one, and listen for what it assumes.

Describing the Item

    def get_items_string(self):
        """Gets description of items in the room"""
        if not self.items:
            return ""
        for item in self.items:
            item_str = item.get_title() + "is laying on the ground.
"
        return item_str

If the room has no items, the method returns an empty string, so nothing extra is said. Otherwise it builds a sentence about the item.

There is a real problem here that you can hear when you play: there is no space before is. The game says a little Gold boxis laying on the ground., and a screen reader reads boxis as one strange word. The right word is also “lying,” not “laying.”

Notice how the loop works. Each time through, item_str gets a brand new value, and the old one is thrown away. With one item, that is fine. This is a good habit to notice, though: setting a variable inside a loop keeps only the last value. If you ever want a loop to collect several things, start with an empty string before the loop and use += inside it.

A Method That Is Never Used

    def get_item(self, name):
        """get an item from this room by given name"""
        i = self.items[name]
        del self.items[name]
        return i

self.items is a list. A list needs a number for an index, but name is a string, so self.items[name] would cause a TypeError. This method treats the list as if it were a dictionary.

The game never calls get_item(), so the problem never shows up. Code that is never used can hide mistakes for a long time. Since remove_item() does this job, get_item() can be deleted.

Picking Up the Item

    def remove_item(self, item):
        """Remove this item from room"""
        if not self.items:
            return None
        for i in range(len(self.items)):
            if self.items[i].is_name(item):
                tItem = self.items[i]
                del self.items[i]
                if len(self.items) < 1:
                    self.items = None
                    return tItem
        return None

The parameter item is the name the player typed, such as "box". The method looks for an item with that name. When it finds one, it saves it in tItem, removes it from the list with del, and returns it.

del removes an item from a list by its index:

>>> things = ["a", "b", "c"]
>>> del things[1]
>>> things
['a', 'c']

Trace it with the game’s one item. The room’s list holds the gold box. The player types get box. The loop finds the box at index 0, saves it, and deletes it. Now the list is empty, so self.items is set back to None, and the box is returned. It works.

Listen carefully to the indentation of return tItem, though. It is inside the if len(self.items) < 1: block. That means the method only returns the item when the room is left empty. That is always true in this game, because a room never holds more than one item. The code depends on the game’s design.

Writing down assumptions like this is a good habit. A one-line comment such as # A room holds at most one item. tells the next programmer, who might be you in a few months, what the code expects. If you ever change the design, the comment reminds you which methods to rewrite. To work with any number of items, the return would move out of the inner if, so the method returns as soon as it finds the item:

        for i in range(len(self.items)):
            if self.items[i].is_name(item):
                found = self.items[i]
                del self.items[i]
                if not self.items:
                    self.items = None
                return found
        return None

Returning right away also avoids a trap you should know about in general: changing a list while you loop over its indexes. After a del, the list is shorter, but a loop set up with range() still goes up to the old length.

The Linter Report

room.lnt is the output of pylint, a popular linter for Python. A linter reads your code without running it and reports problems, from real bugs to style advice. Each line of the report gives the file, the line and column, a code, and a message.

The report in this folder was made from an older version of room.py, so the line numbers and names do not match the current file. You can see that the code was improved since then. Method names like setDirection were changed to set_direction, and docstrings were added. Some messages are about problems that are still there, such as:

room.py:37:15: C0121: Comparison 'self.exits[u] != None' should be 'self.exits[u] is not None' (singleton-comparison)

Linter reports are plain text, one problem per line, which makes them very easy to read with a screen reader. Many blind programmers rely on linters to catch the small mistakes that are hard to hear, like a missing space or a stray line.

To make your own report, install pylint and run it on the file:

pip install pylint
pylint room.py

Summary

You studied the Room class. You learned that:

  • A dictionary holds key and value pairs in curly braces, and looks up a value by its key.
  • items() gives you each key and value in a for loop.
  • Use is None and is not None to check for None.
  • del removes an item from a list by index.
  • Setting a variable inside a loop replaces its old value each time.
  • Watch where a return is indented. It decides when the method returns.
  • Code often depends on the program’s design. A comment can record that.
  • Changing a list while looping over it can cause bugs.
  • Linters find problems by reading your code, and their reports are easy to hear.
