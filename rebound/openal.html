Inside openal.py: Reading a Library You Did Not Write

The Rebound game moves the ball’s sound around your head using a file called openal.py. That file is about 4,000 lines long, and it was not written for Rebound. It is a library: code written by other people, for anyone to use. Its job is to let Python programs talk to OpenAL, a sound library written in the C programming language.

You will not read all 4,000 lines in this lesson, and you do not need to. A big part of being a programmer is learning how to find your way around a large file, find the parts you need, and understand them well enough to use them and fix them. This lesson shows you how, with a screen reader, and explains the parts of openal.py that Rebound uses.

This is the most advanced lesson in these materials.

A Note on Reading Code with a Screen Reader

Python uses indentation, the spaces at the start of a line, to show which lines belong together. A line that ends with a colon, such as while True: or def main():, starts a block. Every line in that block is indented four more spaces than the line with the colon.

Before you start, turn on indentation reporting in your screen reader or code editor so you hear how far each line is indented. In NVDA this setting is called “Line indentation reporting” and is under Document Formatting. JAWS and most code editors have a similar setting. Many blind programmers like to hear indentation as tones, but spoken numbers work too.

It also helps to set your screen reader to read all punctuation while you are working with code. Punctuation matters in Python. A missing colon, quote, or parenthesis is one of the most common errors.

In this lesson, code you type into a file is shown in code blocks. Code you type into the interactive shell starts with three greater-than signs, >>>. That is the shell’s prompt. Do not type the prompt. Type only what comes after it. The lines with no prompt are what Python prints back.

Do Not Type This One In

Unlike the other lessons, you should not type this file in. It is long, it was generated partly by a tool, and it already works. Instead, open it in your editor and follow along. The full file is in the rebound folder. This lesson shows only short pieces of it.

What Is a Wrapper?

OpenAL is written in C, and on Windows it comes as a file called OpenAL32.dll. A DLL, or dynamic link library, is a file of compiled code that programs can load and use while they run. Python cannot use C code directly. It needs a translator.

openal.py is that translator. Code that makes a library written in one language usable from another is called a wrapper, or a binding. It “wraps” the C functions in Python functions and classes.

The file has two layers:

  1. A low-level layer that matches OpenAL’s C functions one for one, such as alSourcePlay. These are in the classes lib_openal, lib_alc, and lib_efx.
  2. A high-level layer of friendly Python classes, such as Listener, LoadSound, and Player, that use the low-level layer. Rebound only uses this layer.

Finding Your Way Around

A file this long is hard to read from top to bottom with any tool, and especially by ear. Here are some techniques that work well with a screen reader.

Search for Classes and Functions

Use your editor’s Find command to search for class, with a space after it. Each match is the start of a class. In openal.py you will find these, among others:

  • lib_openal, lib_alc, and lib_efx, the low-level layer
  • Listener, the listener, or your ears
  • LoadSound, a sound loaded from a WAV file
  • BufferSound, a sound made from raw data
  • Player, a sound source that plays sounds
  • Effects such as reverb, echo, chorus, and distortion
  • Filters such as lowpass_filter

Searching for def works the same way for functions and methods.

Use a Command-Line Search

You can also search from the command prompt. On Windows, findstr lists every line that matches, with its line number:

findstr /n /b "class" openal.py

/n adds line numbers, and /b only matches at the beginning of a line. The result is a short list, one class per line, which is much easier to hear than the whole file. On Mac or Linux, grep -n "^class" openal.py does the same.

Start from What You Use

You do not need to understand the whole library. Start from the lines in Rebound that use it, and find only those parts:

listener=openal.Listener()
listener.distance_model=5
listener.position=(width/2, height-40, 0)
ball_sound=openal.LoadSound('sounds/ball.wav')
ball_source=openal.Player()
ball_source.add(ball_sound)
ball_source.position=(width/2, height-50, 0)
ball_source.loop=True
ball_source.rolloff=0.1
ball_source.reference_distance=0.1
ball_source.play()
ball_source.pitch=get_pitch(ball_position[1])

So you need Listener, LoadSound, and Player, and a few of their attributes and methods. That is a small part of 4,000 lines.

The License

The file begins with a long comment. It is a license: the legal terms for using this code. The code was originally part of pyglet, a Python library for games, written by Alex Holkner. This license, a type called a BSD license, lets anyone use and change the code, as long as they keep the copyright notice and do not use the authors’ names to promote their own products.

Whenever you use code someone else wrote, check its license, and keep their notice. Credit matters. Rebound does the same, crediting its author at the top of rebound.py.

After the license, a docstring explains that the low-level part was generated by a tool called wrap.py from OpenAL’s C header file, al.h, and then changed by hand. Much of the low-level code was written by a program, not a person, which is why it is so long and so repetitive.

Loading the DLL with ctypes

import ctypes
from ctypes import *

ctypes is a module that comes with Python. It lets Python load DLLs and call the C functions inside them.

from ctypes import * imports every public name from ctypes. That saves typing, but it makes it hard to tell where a name came from, so most style guides advise against it.

class lib_openal(object):
    def __init__(self):
        if 'add_dll_directory' in dir(os):
            os.add_dll_directory(os.getcwd())
            self._lib = ctypes.CDLL('OpenAL32.dll')
        else:
            self._lib = ctypes.CDLL(os.path.abspath('OpenAL32.dll'))

ctypes.CDLL() loads a DLL and returns an object whose attributes are the C functions inside it.

Newer versions of Python on Windows only load DLLs from certain safe folders. os.add_dll_directory() adds a folder to that list. dir(os) lists every name in the os module, so the if checks whether this Python has that function. Either way, the DLL is looked for in the current working directory. That is why you must run Rebound from the rebound folder.

Describing C Functions to Python

        self.alSourcePlay = self._lib.alSourcePlay
        self.alSourcePlay.restype = None
        self.alSourcePlay.argtypes = [self.ALuint]

C is strict about types. Every argument and return value has a fixed type, such as a whole number or a decimal number of a certain size. Python is not strict in the same way, so ctypes needs to be told.

  • restype is the return type. None means the function returns nothing.
  • argtypes is a list of the argument types. alSourcePlay takes one ALuint, an unsigned whole number that identifies a sound source.

The low-level classes do this for hundreds of functions. That is most of the file. When you hear long runs of nearly identical lines, you are in generated code, and you can usually skip ahead.

Constants

        self.AL_PITCH = 4099    # /usr/include/AL/al.h:145
        self.AL_POSITION = 4100     # /usr/include/AL/al.h:157

OpenAL uses numbers to name its settings. AL_POSITION is 4100. These lines give the numbers readable names. The comments say where each was found in the C header file.

Objects Made on Import

#initialize openal bindings
al = lib_openal()
alc = lib_alc()
efx = lib_efx()

These three lines are not inside any class or function, so they run as soon as the module is imported. When Rebound says import openal, the DLL is loaded right away, and the objects al, alc, and efx are ready for the rest of the file to use.

This means that if OpenAL32.dll is missing, the error happens on the import openal line itself, before any of your code runs. If you ever see an error on an import line, check whether the library needs a file that is missing.

The Listener Class

class Listener(object):
    def __init__(self):
    #load device/context/listener
        self.device = alc.alcOpenDevice(None)
        self.context = alc.alcCreateContext(self.device, None)
        alc.alcMakeContextCurrent(self.context)
        alc.alcProcessContext(self.context)

A listener is the position of the person hearing the sounds. In Rebound, it is your paddle.

Making a Listener also opens the sound device, which is your sound card or headphones, and creates a context, which is OpenAL’s workspace. Passing None to alcOpenDevice() means “use the default device.” This is why a program must make a Listener before any sounds can play.

(object) after the class name is an older way to write a class. In Python 3, class Listener: means the same thing.

Notice the comment, #load device/context/listener, is at the left edge, but the code around it is indented. Python does not care how comments are indented, but it is confusing to hear. Indentation is meant to show structure, and a comment at the wrong level makes it sound like the method has ended.

Properties

#set listener position
    def _set_position(self,pos):
        self._position = pos
        x,y,z = map(float, pos)
        al.alListener3f(al.AL_POSITION, x, y, z)

    def _get_position(self):
        return self._position

and near the end of the class:

    position = property(_get_position, _set_position,doc="""get/set position""")

This is how listener.position = (400, 560, 0) in Rebound can tell OpenAL to move the listener, even though it looks like setting an ordinary attribute.

property() makes a property. A property looks like an attribute from the outside, but reading it calls a getter method, and setting it calls a setter method. So:

  • listener.position = (400, 560, 0) calls _set_position((400, 560, 0)).
  • listener.position calls _get_position().

The setter saves the new position, and then calls the C function alListener3f() to tell OpenAL. That is the whole trick of a good wrapper: it hides the C calls behind something that feels like normal Python.

Underscores Mean “Private”

The getter and setter are named _get_position and _set_position, starting with an underscore. The saved value is self._position. In Python, a name that starts with one underscore is a signal: “This is for use inside the class. Do not use it from outside.” Python does not enforce this. It is a promise between programmers, like constants in capital letters.

Users of the class should use the public property, position, and leave the underscore names alone.

map()

        x,y,z = map(float, pos)

map() calls a function on every item of a list or tuple. Here it turns each of the three numbers into a decimal number, a float, because the C function needs floats. Then the three results are unpacked into x, y, and z.

>>> x, y, z = map(float, (400, 560, 0))
>>> x
400.0

The Distance Model

listener.distance_model = 5 in Rebound calls _set_distance_model(5), which uses if and elif to turn the number into an OpenAL setting. Model 5 is AL_EXPONENT_DISTANCE. A distance model is the rule for how much quieter a sound gets as it moves farther from the listener. With the exponential model, the volume drops off quickly at first and then more slowly.

The LoadSound Class

class LoadSound(object):
    def __init__(self,filename):
        self.name = filename
    #load/set wav file
        if len (sys.argv) < 2:
            print("Usage: %s wavefile" % os.path.basename(sys.argv[0]))
            print("    Using an example wav file...")
            dirname = os.path.dirname(os.path.realpath(__file__))
            fname = os.path.join(dirname, filename)
        else:
            fname = sys.argv[1]

LoadSound reads a WAV file and copies its sound data into OpenAL. Before you read on, listen to the if statement carefully. Something is odd.

A Bug Hiding in a Library

sys.argv is the list of words typed on the command line. sys.argv[0] is the program’s name, and anything after it is extra. When you run python rebound.py, sys.argv is ["rebound.py"], which has fewer than 2 items, so the first block runs. It prints a “Usage” message, which you will hear in the command prompt every time a sound is loaded, and then builds the path to the file.

But if you ran python rebound.py fast, sys.argv[1] would be "fast", and every sound would try to load a file named fast, instead of the file the program asked for. The game would crash.

This code was clearly copied from a small example program that took a sound file name on the command line. In an example, that makes sense. In a library, it is a bug. A library should only use the arguments it is given, and never read the command line or print messages of its own. The fix is to remove the if and always use the file name that was passed in.

Where the File Is Found

            dirname = os.path.dirname(os.path.realpath(__file__))
            fname = os.path.join(dirname, filename)

__file__ is the path of the current module, openal.py. os.path.realpath() makes it a full path, and os.path.dirname() takes off the file name, leaving the folder. So sound files are found relative to the folder openal.py is in, not the folder you ran the program from.

That is a good way to find files that come with a program. It is more reliable than the os.getcwd() approach from the dice lessons, which depends on where you are when you run the program.

Reading a WAV File

        wavefp = wave.open(fname)
        channels = wavefp.getnchannels()
        bitrate = wavefp.getsampwidth() * 8
        samplerate = wavefp.getframerate()
        wavbuf = wavefp.readframes(wavefp.getnframes())

The wave module comes with Python and reads WAV files. A WAV file stores sound as a long list of numbers called samples. This code asks the file for:

  • The number of channels: 1 for mono, 2 for stereo.
  • The size of each sample in bytes, times 8 to get bits.
  • The sample rate: how many samples per second, often 44,100.
  • All of the sample data, with readframes().

A Dictionary with Tuple Keys

        formatmap = {
            (1, 8) : al.AL_FORMAT_MONO8,
            (2, 8) : al.AL_FORMAT_STEREO8,
            (1, 16): al.AL_FORMAT_MONO16,
            (2, 16) : al.AL_FORMAT_STEREO16,
        }
        alformat = formatmap[(channels, bitrate)]

Dictionary keys can be tuples. This dictionary matches a pair of channels and bits to the OpenAL format name. It is a neat replacement for four if statements.

Positional Sound Needs Mono

Here is something important about 3D sound. OpenAL can only place a mono sound in 3D space. A stereo sound already has its own left and right, so OpenAL plays it as it is, without moving it. If you replace ball.wav with a stereo file, the ball will stop moving around your head. Always use mono files for sounds that need a position.

Freeing the Sound

        self.buf = al.ALuint(0)
        al.alGenBuffers(1, self.buf)
        al.alBufferData(self.buf, alformat, wavbuf, len(wavbuf), samplerate)

#delete loaded sound
    def delete(self):
        al.alDeleteBuffers(1, self.buf)

The sound data is copied into an OpenAL buffer. The buffer lives inside the C library, outside of Python. Python cleans up its own objects automatically when they are no longer used, but it does not know about memory that a C library is holding. That is why the class has a delete() method, and why Rebound calls ball_sound.delete() at the end. Things a program must remember to give back, such as files, windows, sound devices, and buffers, are called resources.

The Player Class

class Player(object):
#load default settings
    def __init__(self):
    #load source player
        self.source = al.ALuint(0)
        al.alGenSources(1, self.source)
        ...

A Player is an OpenAL source: a point in space that plays sound. Its __init__() asks OpenAL for a new source and sets about two dozen attributes to their defaults.

The methods Rebound uses are short:

    def add(self,sound):
        al.alSourceQueueBuffers(self.source, 1, sound.buf) #self.buf
        self.queue.append(sound)

    def play(self):
        al.alSourcePlay(self.source)

add() gives the source a sound to play, and play() starts it.

The settings Rebound changes are all properties, just like the listener’s position:

  • position places the source in 3D space. Rebound moves it with the ball every frame.
  • pitch changes the playback speed. 1.0 is normal, 2.0 is twice as fast and an octave higher. Rebound uses this to let you hear the ball’s height.
  • loop makes the sound repeat. Rebound’s ball sound loops forever.
  • rolloff is how fast the sound gets quieter with distance. 0 means it never gets quieter. Rebound uses a small value, 0.1, so the ball fades only a little as it goes far away, and you never lose track of it.
  • reference_distance is the distance at which the sound is at full volume before it starts to fade.
  • volume sets the loudness, from 0.0 to 1.0.

For example:

#set whether looping or not - true/false 1/0
    def _set_loop(self,lo):
        self._loop = lo
        al.alSourcei(self.source, al.AL_LOOPING, lo)

Every setter has the same shape: save the value in an underscore attribute, and call an OpenAL function to apply it. Once you have understood one, you understand them all. Recognizing patterns like this is what makes a large file manageable.

3D Sound for Games

With just these few classes, you can do a lot in an audio game:

  • Put the listener where the player is.
  • Make a source for each thing the player needs to track: an enemy, a ball, a door, a goal.
  • Move each source every frame to its object’s position.
  • Use pitch, volume, or a looping sound to give extra information, such as height, speed, or danger.

The listener’s position is in the same units as the game, here pixels. So the sound of the ball 400 pixels to the left of the paddle is placed far to the left. With headphones, many players can follow a moving sound very precisely.

Summary

You explored a large library you did not write. You learned that:

  • A wrapper lets one language use a library written in another.
  • Always check the license of code you use, and keep its notice.
  • Search for class and def, or use findstr or grep, to find your way around a big file. Start from the parts your program uses.
  • ctypes loads DLLs and calls C functions. restype and argtypes describe them.
  • Code at the top level of a module runs when the module is imported.
  • property() makes an attribute that calls a getter and setter.
  • A leading underscore marks a name as private by agreement.
  • map() calls a function on every item.
  • The wave module reads WAV files.
  • Dictionary keys can be tuples.
  • Resources held by C libraries must be freed with methods like delete().
  • OpenAL places mono sounds in 3D space around a listener, with position, rolloff, reference distance, and pitch.
  • A library should never read sys.argv or print messages of its own.
